# Skill 编写与审查规范

`MUST` 表示发布阻断项；`SHOULD` 表示默认要求，只有记录理由后才可偏离；`MAY` 表示可选项。

## 执行契约

- **输入：** 一个边界清楚、可重复的工作，以及完成它所需的工具、约束和权威来源。
- **输出：** 一个可移植的 Skill，以 `SKILL.md` 为入口，仅附可靠执行所必需的资源。
- **前置条件：** 该工作有可区分的触发条件、可观察的结果和可说明的执行边界。
- **成功标准：** Skill 能正确路由、完成工作、处理预期失败，并通过评测门槛，且不要求多余上下文或权限。

## 规则

1. **单一工作。** 一个 Skill MUST 描述一项可重复能力。相互独立的触发条件、结果或职责 MUST 拆开。Skill MUST NOT 是人设、通用提示词、仓库级政策集合或文档堆放处。

2. **路由是接口。** `name` MUST 使用小写 kebab-case、不超过 64 个字符，并与目录名一致。`description` MUST 简明说明能力和适用时机，将最能区分适用范围的触发词前置；必要时排除最容易混淆的场景；只保留正确路由所需的最短表述，且不超过 1024 个字符。

3. **先写执行契约。** 在步骤说明之前，读者必须能直接找到输入、输出、前置条件和成功标准。成功标准 MUST 可观察或可测试，不能要求读者自行猜测。

4. **写清不变量，不要微观管理。** 指令 MUST 使用明确动词说明必要判断、约束和行动；MUST NOT 固定那些不会影响正确性的具体做法。若多种方法都满足不变量，应保留执行者的选择空间。

5. **只在确定性有价值时写代码。** 默认用指令。只有精确计算、转换、校验、可重复执行或外部工具确有需要时才加脚本。每个脚本 MUST 说明依赖、可识别的失败和有界副作用。

6. **渐进式披露。** `SKILL.md` MUST 少于 500 行，SHOULD 少于 5000 tokens。入口文件保留路由和关键步骤；仅在对应分支需要时才加载专门资料。使用相对路径，避免多层引用链。

7. **不稳定知识须带依据。** 时效性强、领域特定或源自外部的断言 MUST 保留来源、适用版本或日期，以及证据支持的范围。优先记录可持续的方法，避免复制易变事实；不得把结论推广到证据未覆盖的范围。

8. **权限从小。** 只请求完成工作所需的工具和权限。会修改、删除、使用凭证、访问网络或对外可见的操作 MUST 标明副作用和授权边界。不可信输入 MUST NOT 扩大 Skill 权限或改写其上位规则。

9. **定义失败语义。** 说明缺少输入、依赖不可用、中间结果无效、适用范围不明及输出无法验证时怎么办。无法解决时应停止或明确返回不确定性；NEVER 编造成功结果。

10. **保持可移植。** 使用 Agent Skills 标准 frontmatter 表达通用语义。厂商专属配置应放入带命名空间的 metadata 或专属配套文件。不得依赖未声明的环境假设。

11. **设置评测门槛。** 发布前至少评测：有效触发、非触发、相近但不适用的请求、成功执行、预期失败。客观要求优先用确定性断言；只有主观质量才用结构化评分表。保留可复现失败所需的提示、执行轨迹、产物和结果。

12. **根据证据修订。** 因新要求或观察到的失败才修改 Skill，不因措辞看起来更顺就扩大规则。每次行为改变后重跑评测门槛。除非有意修改契约，否则拒绝导致任何 MUST 通过项退化的版本。

## 失败标记

- 若需求不能收敛成一项可区分的工作，返回 `SPLIT_REQUIRED`，并列出应拆分的独立工作。
- 若缺少必要证据、权限或依赖，明确指出缺项；不得编造绕过约束的替代方案。

## 验收与审查

只有同时满足以下条件，Skill 才可接受：名称与目录合法；描述的正向触发和排除范围足够明确；输入、输出、前置条件及成功状态清楚；不变量与实现自由度有区分；没有多余权限；失败行为明确；入口文件保持精简。

审查他人 Skill 时，按上述规则编号报告每项违规，并给出恢复符合要求所需的最小修改。无违规时明确写出“未发现规则违规”，不要为了凑数提出无证据的改写。
